# Этап 6. Сценарные тесты и проверка качества персонального анализа

## Как устроен прогон

Автоматические сценарии запускаются без сети и без настоящего Groq API key. Расчётные сценарии передают фикстуры непосредственно в \`build_personal_trends\`; API-сценарии используют изолированную SQLite-базу и FastAPI TestClient; вызов Groq заменён mock-ответом или mock-ошибкой. Frontend regression test проверяет контракт между HTTP-ответом, строгой проверкой payload и отображаемыми секциями страницы.

Команда для backend из каталога \`backend\`:

\`python -m unittest discover -s tests\`

Команда для frontend из каталога \`frontend\`:

\`npm test\`

## Матрица ожидаемых свойств

| № | Сценарий и фикстура | Обязательное ожидаемое свойство |
|---:|---|---|
| 1 | Полная 28-дневная история, стабильные самочувствие и сон, тренировки и RPE | Тренды готовы и помечены как stable; число наблюдаемых дней совпадает с фикстурами; значения покрытия отражают фактические записи. |
| 2 | Четыре дня низкого sleep score, субъективное самочувствие и тренировочная нагрузка стабильны | Сон получает downward, самочувствие остаётся stable, количество тренировок не падает из-за изменения сна. Не объединять метрики в общий score. |
| 3 | Самочувствие падает с 5 до 2 в последнем окне | Расчёт показывает точную разницу -3 и downward; интерпретация не ставит диагноз и не выводит причинность. |
| 4 | В текущем окне только два завершённых утренних чек-ина, есть skipped/pending | Тренд недостаточен, реальные средние могут присутствовать, но change/trend для сравнения не утверждают вывод; пропуски отражены отдельно и не превращены в нули. |
| 5 | Тренировки есть, послетренировочных RPE почти нет | RPE покрытие и activities_without_rpe совпадают с фикстурой; недостаток отметок не трактуется как низкий RPE. |
| 6 | Есть только один-два дня истории | Возвращается insufficient_data для сравнения, change не выдумывается, Groq не вызывается при общем insufficient_data. |
| 7 | Самочувствие улучшается, sleep score ухудшается | Каждая метрика сохраняет собственное направление; combined_score не создаётся, конфликт не «усредняется». |
| 8 | После нескольких пустых дней пользователь возвращается | В расчёт попадают только реальные значения; mean использует доступные дни, days_with_data отражает их число, пустые дни присутствуют в data_gaps/coverage. |
| 9 | Две тренировки в один локальный день | RPE усредняется внутри дня, TSS дня равен сумме полных измеренных TSS всех тренировок, количество занятий не путается с количеством календарных дней. |
| 10 | Повторно создаётся утренний чек-ин с тем же user_id/local_date | Уникальность пары user_id + local_date не даёт создать вторую строку; сохранённое значение не перезаписывается посторонней дублирующей вставкой. |
| 11 | Время тренировки возле полуночи UTC и смена IANA timezone | Дата рассчитывается по выбранному timezone; один и тот же instant может принадлежать разным локальным датам; неизвестная зона безопасно fallback-ится в UTC с предупреждением в данных. |
| 12 | Timeout, network error, upstream 429/503 и некорректный JSON | Ошибка имеет корректную безопасную категорию; ключ, prompt и body провайдера не появляются в исключении/API; AI-ошибка не ломает детерминированные тенденции. |
| 13 | \`PERSONAL_ANALYSIS_AI_ENABLED=false\` или отсутствует \`GROQ_API_KEY\` | API возвращает 503, провайдер не вызывается, страница сохраняет обычные тенденции и показывает ошибку конфигурации. |
| 14 | Mock-модель возвращает выдуманное число, отрицает известные пропуски или утверждает причинность | Ответ отклоняется как unsupported_claim и не доходит до рендера. Допустим только структурно корректный ответ без обнаруживаемых неподтверждённых чисел/причинных фраз и с признанием известных пробелов. |
| 15 | Два пользователя с противоположными чек-инами, запрос от имени первого | API использует только user_id текущей сессии; в JSON нет данных/идентификатора другого пользователя; запрос интерпретации не изменяет источник записей. |

Функциональные проверки и регрессии, которые уже находились в прежних тестах, остаются активными: авторизация, допустимые периоды, отклонение invalid schema/JSON, проверка ключа, базовые timezone cases и минимизация данных, отправляемых Groq.

## Пределы автоматической проверки модели

Quality gate детерминированно проверяет JSON-схему, числовые литералы на наличие в агрегированных входных данных, признание data gaps и распространённые формулировки причинности. Это не универсальный семантический fact-checker: он не может доказать истинность любой фразы на естественном языке или обнаружить каждую перефразированную галлюцинацию. Поэтому в ответе остаются обязательными prompt-ограничения, агрегированный минимизированный input, описание ограничений и ручная проверка.

## Ручная проверка с настоящим Groq API

1. На тестовом аккаунте с полным набором сохранённых чек-инов откройте приватную страницу анализа, загрузите период 28 дней и нажмите AI-интерпретацию. Проверьте русский текст, формат всех четырёх списков, соответствие показанным трендам и отсутствие новых числовых утверждений.
2. На другом тестовом периоде оставьте намеренные пропуски, а сон и субъективную готовность сделайте разнонаправленными. Убедитесь, что модель описывает показатели раздельно и явно отмечает неполноту данных.
3. Повторите запрос на минимальной истории: ожидается insufficient_data без вызова провайдера. После возврата к достаточной истории запрос должен работать снова.
4. В Render временно отключите AI через \`PERSONAL_ANALYSIS_AI_ENABLED=false\`, дождитесь redeploy и убедитесь, что endpoint отвечает 503 и обычные детерминированные тенденции доступны. Затем включите настройку обратно.
5. Проверьте конфигурацию без раскрытия секрета: отсутствующий ключ должен давать 503; неверный тестовый ключ — безопасную ошибку авторизации; квота или лимит — безопасную подсказку HTTP 429. После проверки восстановите корректный ключ. Не вставляйте секрет в issue, PR, скриншот или чат.
6. Проверьте timeout и доступность провайдера через mock в автотестах; необязательно искусственно ломать production-сервис. При ручной проверке изучите только безопасную строку Render Logs с category/status/model; никаких ключей, prompt, персональных значений и upstream response body в логах быть не должно.
7. Осмотрите отображение ответа на desktop и mobile: заголовок, summary, positive/caution signals, steps и limitations; для некорректной схемы должен быть показан безопасный error state, а не частичный JSON или сырой текст модели.

## Переключатель AI

\`PERSONAL_ANALYSIS_AI_ENABLED\` — серверная переменная окружения, по умолчанию true для совместимости с текущим поведением. Её можно выключить без удаления ключа и без изменения детерминированного анализа. Для production после изменения Environment в Render требуется дождаться завершения redeploy.
